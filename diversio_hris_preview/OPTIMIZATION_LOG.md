# Optimisation log

A record of every change considered, what it measured, and what was decided.
Kept because the decisions matter more than the numbers: several plausible
optimisations measured worse than the code they replaced, and two measurements
were wrong the first time.

Working file for all figures: 100,015 rows, 5.1 MB, generated by
`benchmarks/make_large_csv.py`. Timings are medians of 9–15 interleaved runs
with the garbage collector disabled. Absolute numbers drift a few percent
between sessions on shared hardware, so **ratios within a session are
meaningful and absolute values across sessions are not.**

---

## Round 1 — first working version

Straightforward implementation: `csv.DictReader`, two `Counter` passes for
duplicate detection, a full sort of every manager, and twelve traversals of the
data end to end.

| | |
|---|---|
| Result | ~0.61 s baseline |
| Traversals | 12 |

**Measurement error, caught and corrected.** The first timing reported 3.69 s.
That was `tracemalloc`'s own tracing overhead, not the code — it traces every
allocation. Re-measured without it: 0.71 s. Memory has to be measured
separately, with `resource.getrusage`, not alongside timing.

---

## Round 2 — fusing the parse into one pass

Built the identity indexes inside the read loop so duplicate detection came
free, and skipped the reconciliation pass entirely for clean files. Seven
traversals removed.

| | |
|---|---|
| Measured | **1.00x — no faster, no smaller in memory** |
| Decision | **reverted** |

The removed passes were C-level `dict` and `Counter` operations over cache-warm
data. Moving the same inserts into the Python-level read loop cost back what
they saved. **Pass count is not cost.**

**This measurement was also wrong.** It was a single-shot comparison. Re-run
interleaved over 15 pairs in Round 4, the same change measured 1.03–1.05x
against a run-to-run standard deviation of ~5% — real, but at the noise floor.
The revert still stood: it needed a six-parameter helper and coupled the parse
result to a later stage's needs.

Three changes from the attempt were kept, because they removed genuinely
duplicated computation at no complexity cost:

- `direct_reports` counted as each edge is created, not in a later pass
- the presentation layer reuses `Hierarchy.by_id` instead of rebuilding it
- cycle rows looked up by id, O(c), instead of scanning all n employees

| | |
|---|---|
| Result | 3.1% faster, 12 → 9 traversals |

## Round 3 — bounded heap for ranking

Ranking managers was the only super-linear step in the pipeline: O(n + m log m).
Only the top 100 are ever displayed, so a full sort of 50,160 managers was
discarding 50,060 of them.

`heapq.nsmallest(100, ...)` is O(m log k) for fixed k — which is O(m), making
the whole pipeline linear. It also builds 100 summary objects instead of m.

| | |
|---|---|
| Measured | **6.4 ms vs 21.2 ms — 3.31x**, identical output |
| Decision | **applied** |

Templates were also de-duplicated in this round: five near-identical table
blocks became two `{% include %}` partials, 138 → 64 lines plus 39 of partial.

---

## Round 4 — fixed column offsets instead of DictReader

`csv.DictReader` builds a dict for every row. Resolving each required column to
an integer offset once and reading `row[i_email]` avoids that entirely.

| | |
|---|---|
| Measured | **1.51x on the parse stage — 122 ms, 24% of total runtime** |
| Decision | **applied** |

The error handling got simpler rather than more complex: one
`len(row) != width` check replaces `restval`/`restkey` and produces a better
message for the unquoted-comma case, which is the commonest real CSV defect. A
test was added for it.

---

## Round 5 — seen-sets for duplicate detection

Replaced the two `Counter` passes with two sets maintained during the read
loop: a key already in the set is a repeat. When a file has no duplicates —
the normal case — the reconciliation pass is skipped entirely.

| | |
|---|---|
| Measured | **1.44x on the parse stage — 74 ms, 18% of total** |
| Decision | **applied**, 12 → 6 traversals (5 for a clean file) |

This is the change Round 2 was reaching for and got wrong. The difference:
Round 2 also built the *dicts* in the read loop. `dict[key] = row` costs more
per row than `set.add(key)`, and that difference more than paid back the
rebuild it saved. Keeping the "redundant" index build in `Hierarchy` is faster
than sharing the state.

What no version of this can remove is the reconciliation pass itself when
duplicates *do* exist. The contract invalidates the first occurrence too, so a
row accepted at line 2 has its verdict revised by a collision at line 900,000.
Comparing sizes (`len(pending) - len(seen)`) gives the *number* of excess rows
in O(1), but the requirement is row-level errors with source row numbers, which
needs to know *which* rows.

## Round 6 — positional dataclass construction

Profiling every function turned up ~30 ms inside `parse_employees` that
subtraction could not attribute. The cause was keyword arguments: CPython
matches seven keyword names on every `EmployeeRow(...)` call.

| | |
|---|---|
| Measured | **34.6 ms per 100k rows — 16% of parse, 9% of total** |
| Decision | **applied** |

Positional construction is where a field-order bug would hide, so the guard was
strengthened: the differential harness now compares *every field of every row*
against the original implementation across 100 generated files.

---

## Round 7 — packing walk position into the state map

`_find_cycle_members` kept two dictionaries per walk: `state` and `position`.
The state map now does both jobs — it holds the node's index in the current
path while the node is on it, and `-1` once the node is settled.

| | |
|---|---|
| Measured | **43.6 ms vs 38.5 ms — 1.13x** |
| Decision | **applied**, and it deleted one dict and two module constants |

---

## Round 8 — dictionary encoding for low-cardinality columns

Borrowed from columnar formats and ML feature pipelines: store each distinct
value of a repeated column once and reference it. 43 distinct departments across
100,009 rows became 43 string objects instead of 100,009.

| | |
|---|---|
| Measured | **64.5 MB to 54.5 MB peak — 15% less memory**, ~1 ms cost |
| Decision | **applied** |

Every other column was checked for cardinality first; `employee_id`,
`email` and `employee_name` are fully distinct, so they are not pooled. The pool
is a request-scoped dict, not `sys.intern`, which would pin values for the life
of the worker process.

This is the only change in the whole log that targets memory rather than time,
and memory is the stated constraint.

## Measured and rejected

Each of these was implemented or prototyped, measured, and dropped.

| Candidate | Measured | Why not |
|---|---|---|
| Fusing indexes into the read loop | 1.03–1.05x | Six-parameter helper and cross-stage coupling for 3% |
| Dense integer ids | 1.66x cycle walk, 6.0x report counts, **7% overall** | Needs an index threaded through every stage. Closest call of the lot. |
| Inlining `_resolve_manager` | 1.07x, 7 ms, 2% | Turns the clearest decision table in the codebase into nested `continue`s |
| Short-circuit required-field check | **slower** (23.4 vs 20.6 ms) | Hypothesis was simply wrong |
| pandas, vectorised | **1.12x only**, and **crashes** on a malformed row | Barely faster, and it refuses to open a file containing the defects this app exists to find |
| polars, vectorised | **4.59x on parse**, also crashes on a malformed row | Genuinely fast — see "further directions" below |
| A rewrite in C++, Go or Rust | 2.2x to **7.0x**, all producing identical output | rejected — the brief requires Python, and the ceiling is 7x, not the 20x usually assumed |
| Trie | — | Answers *prefix* queries; every lookup here is exact match |
| Segment tree | — | Answers *range* queries; no ordering of employees makes a range meaningful |
| Fenwick tree | — | *Prefix sums* in O(log n); we need *point* counts, which a hash map does in O(1). Asymptotically worse. |
| Union-find | — | Can fold cycle detection into resolution, but still needs a walk to enumerate members |
| Queue / Kahn's algorithm | — | Peeling in-degree-0 nodes *does* isolate cycle members correctly, but is more bookkeeping than the pointer walk |
| Bloom filter | — | The real index is needed anyway for manager lookup, so nothing is saved |
| Memoised depth / subtree size | — | Genuine DP with overlapping subproblems, but the spec asks for *direct* reports only |

## A note on measuring

Three figures in this log were wrong the first time, and all three were
measurement errors rather than code errors. They are left described here because
the failure modes recur.

1. **Profiler overhead counted as runtime.** A first timing of 3.69 s was
   `tracemalloc` tracing every allocation. Real answer: 0.71 s. Memory and time
   must be measured separately.
2. **Single-shot comparison on a shared machine.** The parse-fusion experiment
   measured 1.00x once and 1.03–1.05x over fifteen interleaved pairs. Run-to-run
   spread on this hardware is around 5%, so any single measurement below that is
   noise.
3. **Warm against cold.** A cross-language comparison measured Python warm —
   twelve analyses inside one process — but launched a fresh process for each
   compiled run, so every compiled language paid cold-heap page faults that
   Python did not. That understated them by roughly 30% and even reversed the
   ranking between two of them.

The rule that follows: interleave the alternatives, repeat inside one process,
report the minimum, and quote a range rather than a digit when the spread is
wider than the difference being claimed.

## Where it ended

| | Original | Final |
|---|---|---|
| Time, 100k rows | 0.59 s | **0.36 s** |
| Throughput | ~170k rows/sec | **~278k rows/sec** |
| Peak memory | 64.5 MB | **54.5 MB** |
| Traversals | 12 | **6** (5 clean file) |
| Complexity | O(n + m log m) | **O(n)** |
| Dependencies | Django | Django |

Final figures were reproduced across three separate interpreter processes and
agreed to within 0.01x (1.62x, 1.63x, 1.63x). Correctness was cross-checked
against an independent reference implementation over 23,000 generated files with
zero mismatches — including the numpy pointer-doubling result, which was the
claim in this log most deserving of scepticism.

**No asymptotic improvements remain.** Every stage sits at its floor: parsing
O(n), duplicate detection O(n) hashing, manager resolution O(n) hash lookups,
cycle detection O(n) with each node settled once, ranking O(m log k) with k
fixed. Everything from here is constant factors.

## Further directions

Ordered by how much they would actually change, not by how interesting they are.

### 1. Concurrency, not speed — the real ceiling

At 0.35 s for 100k rows the analysis is not the bottleneck. Peak memory of
~50 MB per request is, because it multiplies by concurrent uploads while the
GIL serialises the CPU-bound work anyway. An `async` view would make this
*worse*, not better: it would block the event loop.

The fix is structural, not algorithmic — move the analysis to a task queue
(Celery, or Django 6.0's built-in background tasks), return a job id, and poll.
Everything else on this list is a rounding error next to it.

### 2. A columnar rewrite — measured at 4.08x on the parse stage

polars reads, normalises and marks duplicate groups in 42.6 ms against the
current 174.1 ms. `Series.is_duplicated()` expresses this project's duplicate
rule exactly: every member of a group, not just the repeats.

A full columnar version would look like:

| Stage | Today | Columnar |
|---|---|---|
| Read + normalise | Python loop, 174 ms | `read_csv` + `str.strip_chars()`, 43 ms |
| Duplicate verdicts | seen-sets | `is_duplicated()`, vectorised |
| Id → index | — | `factorize` / `rank`, vectorised |
| Manager resolution | 78 ms Python loop | **self-join** on `manager_id = employee_id` |
| Cycle detection | 44 ms pointer walk | **pointer doubling**, 4.7 ms — see below |

**A correction.** An earlier version of this log claimed cycle detection is
inherently sequential and cannot vectorise. That is wrong. Following a manager
pointer is a loop-carried dependency, but *pointer doubling* sidesteps it:
repeat `p = p[p]` for log2(n) rounds and every node has jumped 2^k steps at
once. Once 2^k >= n, every node has landed on its cycle, and the image of that
map is exactly the set of cycle members — tails leading into a cycle are not in
the image, which is the distinction the specification asks for. O(n log n) work
instead of O(n), and **9.4x faster** anyway: 4.7 ms against 44.2 ms, because
seventeen passes in C beat one pass in Python.

So the end-to-end ceiling is nearer 4x than 2.5x, and the argument against a
columnar rewrite is not that any stage resists it. It is the boundary:

| | |
|---|---|
| Sequential walk (shipped) | 44.2 ms |
| Pointer doubling alone | 4.7 ms — 9.4x |
| String ids → dense integers | 33.6 ms |
| **Doubling including that conversion** | **38.3 ms — 1.16x** |

Vectorising one stage of a row-based pipeline does not pay, because converting
across the row/column boundary costs more than the stage saves.

**The obvious counter-move works, and was measured.** The conversion does not
have to be a separate pass: `by_id` can map an employee id to its *index*
instead of to its row, at identical construction cost, and the manager array can
then be filled inside the resolution loop that already runs. That removes the
boundary cost almost entirely:

| | Hierarchy stage |
|---|---|
| Current (ships today) | 143.3 ms |
| Integer-indexed resolve + Python walk | 138.1 ms — **1.04x, no new dependency** |
| Integer-indexed resolve + numpy doubling | 105.0 ms — **1.36x, needs numpy** |

The decomposition is the decision. Integer indexing on its own buys 4% and is
not worth restructuring for. Every remaining gain — 33.1 ms, 9.2% of the whole
run — is numpy's, and buying it means `requirements.txt` goes from one line to
two for a large binary wheel, to save a third of a tenth of a second on an
operation that already finishes in 0.36 s.

The deciding argument is neither of those. 4x on a 0.35 s operation saves a
quarter of a second, while the actual constraint is ~50 MB per request
multiplied by concurrent uploads — which no parser speed addresses. The
threshold where this flips is files in the millions of rows.
`benchmarks/vectorised_cycles.py` reproduces every number above.

### 3. Files larger than memory

Hashing beats sorting for duplicate detection only while the index fits in RAM.
Past that, the answer inverts: external merge sort on `employee_id`, then a
single linear scan for adjacent duplicates — O(n log n) time but O(1) resident.
Manager resolution becomes a sort-merge join. Cycle detection over a graph that
does not fit in memory is a genuinely harder problem and would want a
graph-processing framework rather than a web request.

### 4. Smaller, measured items not taken

- **Dense integer ids** — 7%, measured. The best remaining pure-Python win.
- **Streaming the response** — the whole result is materialised before
  rendering. Streaming would lower peak memory, not runtime.
- **Request-scoped string pool for `department`** — done, see round 8.
